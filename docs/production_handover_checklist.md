# انتقال به تولید — چه چیزی از مؤسس لازم است تا در یک نشست تمام شود

_ثبت: ۱۴۰۵/۰۵/۱۷. هدف: وقتی دسترسی داده شد، **یک نشست** کافی باشد — نه رفت‌وبرگشت._

> **یک لندینگ، یک کدبیس.** بستهٔ استاتیکِ جداگانهٔ apex **بازنشسته** است.
> `digiinvoice.ir` را همین استک خودمان سرو می‌کند. هر سند قدیمی‌تری که از zip
> آپکس حرف می‌زند، تاریخی است.

## ۱. آنچه فقط مؤسس می‌تواند بدهد (بدون اینها نشست شروع نمی‌شود)

| # | مورد | چرا | وضعیت |
|---|---|---|---|
| ۱ | **دسترسی SSH سرور تولید** — میزبان، کاربر، کلید/رمز، پورت | همهٔ کارها روی خودِ سرور انجام می‌شود | ⬜ |
| ۲ | **کنترل DNS برای `digiinvoice.ir`** — رکورد A برای apex **و** `www` | بدون آن نه سایت بالا می‌آید نه گواهی صادر می‌شود | ⬜ |
| ۳ | تأیید اینکه **پورت ۸۰ و ۴۴۳** روی سرور آزادند و به بیرون باز | پیش‌نیاز certbot (چالش HTTP-01) | ⬜ |
| ۴ | تصمیم دربارهٔ **دادهٔ اولیه**: تولید از صفر شروع شود یا از dev مهاجرت کند؟ | مسیر کاملاً متفاوت است (بند ۵) | ⬜ |
| ۵ | **کلید API کاوه‌نگار تولید** (اگر با dev فرق دارد) | پیامک واقعی | ⬜ |
| ۶ | **`SECRET_KEY` تازهٔ تولید** (هرگز از dev کپی نشود) | امنیت نشست‌ها | ⬜ |
| ۷ | **`MOADIAN_CRED_KEY` تازه، ساخته‌شده روی همان میزبان** | قانون بهداشت کلید مودیان | ⬜ |

## ۲. مقادیر محیطی — dev در برابر تولید

| کلید | dev | **تولید** | چرا |
|---|---|---|---|
| `SMS_ALLOWLIST` | `09120000000,09395508721` | **خالی** | فهرست خالی = همه پیامک می‌گیرند. همین کلید بود که تا امروز پیامک را می‌بلعید — بند ۶ |
| `DEBUG` | true | **false** | `dev_otp` نباید در پاسخ API بیاید |
| `ENVIRONMENT` | dev | **production** | |
| `BACKEND_CORS_ORIGINS` | dev | `https://digiinvoice.ir,https://www.digiinvoice.ir` | |
| `VITE_API_BASE_URL` | dev | `https://digiinvoice.ir/api/v1` | **build-time** — ایمیج فرانت باید با همین ساخته شود |
| `PAYMENT_FRONTEND_BASE_URL` / `PAYMENT_CALLBACK_BASE_URL` | dev | دامنهٔ تولید | بازگشت درگاه |
| `MOADIAN_MODE` | mock/sandbox | **تصمیم مؤسس** | ارسال واقعی به سازمان — پیش‌فرضِ محافظه‌کارانه: mock تا تأیید صریح |
| `ZIBAL_ENABLED` | false | **false در نشست اول** | فعال‌سازی زیبال **عمداً به بعد موکول شده** |
| `ZARINPAL_ENABLED` / `SIM_ENABLED` | sim | تصمیم مؤسس | یکی از درگاه‌ها باید فعال باشد وگرنه خرید کار نمی‌کند |
| `DOCUMENT_CAP_ENFORCED` | خاموش | تصمیم مؤسس | سقف اسناد پلن |
| `PAYROLL_TIER_ENFORCED` | خاموش | تصمیم مؤسس | گیت ماژول حقوق |
| `KAVENEGAR_OTP_TEMPLATE` | `digiotp` | همان | قالب تأییدشده |

> **`inventory_enabled` روی هیچ کسب‌وکاری روشن نیست** و ماژول انبار هنوز UI ندارد؛
> در تولید هم خاموش می‌ماند تا بستهٔ UI برسد. کاری لازم نیست.

## ۳. ترتیب دقیق عملیات (نشست اول)

```
 1. SSH + بررسی: docker compose version (باید v2 باشد؛ v1 ممنوع)
 2. کلون سه مخزن کنار هم (backend / frontend / ops)
 3. cp .env.example .env  →  پرکردن طبق بند ۲  →  chmod 600 .env
 4. docker compose config            # اعتبارسنجی پیش از هر ساخت
 5. docker compose build --no-cache api frontend
 6. docker compose up -d postgres redis   → صبر تا healthy
 7. docker compose up -d api
 8. docker compose exec -T api alembic upgrade head
 9. psql \dt  — «alembic current» هرگز اثبات وجود جدول‌ها نیست (gotcha 3)
10. docker compose up -d frontend
11. nginx + certbot برای apex و www  (docs/server_deploy_runbook.md § Nginx)
12. bash scripts/prod_smoke.sh
13. pnpm harness --base-url https://digiinvoice.ir   ← گیت نهایی
14. نصب تایمر پشتیبان شبانه (docs/server_deploy_runbook.md)
```

## ۴. وضعیت اسکریپت‌ها نسبت به استک امروز

| اسکریپت | وضعیت | نکته |
|---|---|---|
| `scripts/prod_bring_up.sh` | ✅ ساختار درست | `alembic upgrade head` را می‌زند و **جدول‌ها را می‌شمارد** (نه فقط `alembic current`). مهاجرت تازهٔ `inv1405a001` خودکار اعمال می‌شود — تغییری لازم ندارد. |
| `scripts/prod_smoke.sh` | ⚠️ ناقص | امروز فقط health/CORS/OTP/bearer/frontend را می‌زند. **بررسی نمی‌کند** که `SMS_ALLOWLIST` خالی باشد و `DEBUG=false` — یعنی همان دو چیزی که اگر اشتباه بمانند، پیامک تولید را دوباره می‌بلعند. **پیشنهاد: پیش از نشست اضافه شود.** |

## ۵. دادهٔ اولیه — دو مسیر، تصمیم مؤسس

- **الف) شروع از صفر (پیشنهاد):** تولید خالی بالا می‌آید؛ مؤسس کسب‌وکار واقعی
  خودش را می‌سازد. تمیزترین راه؛ هیچ دادهٔ آزمایشی به تولید نشت نمی‌کند.
- **ب) مهاجرت از dev:** `pg_dump` از dev → restore روی تولید. **پرسونای دموی
  دنیای نمونه هم با آن می‌آید** و باید بعدش پاک شود؛ کلیدهای مودیانِ dev نباید
  منتقل شوند. اگر این را می‌خواهید، از قبل بگویید — کار جداگانه‌ای است.

## ۶. درسی که تکرارش ممنوع است

`SMS_ALLOWLIST` روی dev فقط شمارهٔ ساختگیِ `09120000000` را داشت، پس **هر شمارهٔ
واقعی پیش از رسیدن به کاوه‌نگار suppressed می‌شد** و هیچ‌کس نمی‌فهمید، چون دفتر
«sent» ثبت می‌کرد. حالا ستون «تحویل به گیرنده» وضعیت واقعی مخابرات را نشان می‌دهد.
**در تولید این فهرست باید خالی باشد** — و `prod_smoke.sh` باید همین را بررسی کند.

## ۷. پرسش‌های باز (حدس نمی‌زنیم)

1. دامنه فقط `digiinvoice.ir` است یا زیر‌دامنه‌ای هم لازم است (`app.`, `api.`)؟
2. سرور تولید **همان** ماشین dev است یا ماشین تازه؟ اگر همان است، dev کجا می‌رود؟
3. `MOADIAN_MODE` در تولید از روز اول واقعی باشد یا mock تا آزمون دستی مؤسس؟
4. کدام درگاه پرداخت روز اول فعال باشد (زرین‌پال؟ شبیه‌ساز؟) — زیبال که عمداً بعداً.
5. ایمیل/شمارهٔ تماس برای certbot و هشدارهای گواهی؟
6. سیاست پشتیبان: نگهداری چند روز، و مقصد کجا (همان دیسک یا جای دیگر)؟
7. آیا `DOCUMENT_CAP_ENFORCED` و `PAYROLL_TIER_ENFORCED` از روز اول روشن باشند؟
